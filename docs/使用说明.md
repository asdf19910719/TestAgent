## 1. 项目功能概览

### 1.1 解决什么问题

AI 编程工具（Claude Code/Cursor 等）能够快速完成功能开发，但经常出现：

* AI 完成功能后没有系统化测试
* 没有按测试层级（单元/集成/系统/验收）分层验证
* AI 自己开发自己验收，产生确认偏差
* "功能看起来能跑"就宣布完成，缺少真实验证证据

本 Agent 通过 **Claude Code 扩展**（不需要 API key），在开发完成后执行完整 QA 流程。

### 1.2 五档运行模式

| 模式 | 命令 | 触发场景 | 耗时 | 是否可发版 |
|---|---|---|---|---|
| **L0 Spot** | `/qa L0` | 单点改动快速验证 | 10-30 秒 | ❌ |
| **L1 Feature** | `/qa feature <名称>` | 一个功能开发完 | 1-5 分钟 | ❌ |
| **L2 Module** | `/qa module <名称>` | 一个模块/迭代完成 | 10-30 分钟 | ❌ |
| **L3 Release** | `/qa release` | 准备发版 | 30-120 分钟 | ✅ **唯一发版凭据** |
| **L4 Bugfix** | `/qa bugfix <引用>` | 修复缺陷后 | 3-15 分钟 | ❌ |

### 1.3 核心特性

* ✅ **五档模式**：按场景选成本与质量平衡
* ✅ **两角色独立校验**：Designer+Runner 设计与执行，Gatekeeper 独立判定（防自审）
* ✅ **影响面驱动**：CodeGraph 代码图精准选用例，Local 模式兜底
* ✅ **真实测试执行**：Playwright、Vitest、Jest、pytest、go test、cargo test、Gradle 等
* ✅ **检查点恢复**：L3 中断后 `/qa resume` 继续
* ✅ **灵活 bug 引用**：BUG-XXX / TC-XXX / #issue / 关键词 / 自然语言
* ✅ **动态需求路径**：在命令中指定文档目录，自动分类
* ✅ **多框架支持**：BMAD / spec-kit / ai-docs / 通用 docs
* ✅ **多端支持**：Web / Backend / Mobile（Android/iOS/Flutter/RN） / Generic

## 2. 产物清单

### 2.1 目录结构

执行 QA 流程后，目标项目会有：

```
your-project/
├── .claude/                              # Claude Code 扩展
│   ├── commands/qa.md                    # slash command
│   └── agents/
│       ├── qa-test-engineer.md           # Designer+Runner subagent
│       └── qa-gatekeeper.md              # Gatekeeper subagent
├── .qa-agent.yml                         # 项目配置（qa init 自动生成）
├── qa/                                   # QA 数据
│   ├── cases/                            # 用例库（权威源）
│   │   └── F-LOGIN/
│   │       ├── TC-LOGIN-001.yml
│   │       └── TC-LOGIN-002.yml
│   ├── bugs/                             # 缺陷记录（权威源）
│   │   └── BUG-001.yml
│   ├── waivers.yml                       # 风险接受清单
│   ├── run/                              # 执行历史
│   │   ├── last.json                     # 最新运行状态
│   │   ├── history.json                  # 历史滚动窗口
│   │   └── selection.md                  # 本次选中的用例理由
│   ├── final_test_report.md              # 最新测试报告
│   ├── release_gate_report.md            # L3 发版门报告
│   └── feedback/                         # KPI 反馈通道
└── tests/                                # 测试代码（Adapter 生成）
    ├── unit/
    ├── integration/
    ├── system/
    └── acceptance/
```

### 2.2 关键产物说明

#### `qa/cases/<feature>/<id>.yml` —— 测试用例

每条用例独立 YAML 文件，schema：

```yaml
id: TC-LOGIN-001
title: 用户使用正确账号密码登录成功
state: active            # active | review | stale | flaky | retired
feature_id: F-LOGIN
requirement_ids: [REQ-101]
level: system            # unit | integration | system | acceptance | smoke | performance | security
purpose: functional      # functional | exception | boundary | regression
priority: P0             # P0 | P1 | P2 | P3

preconditions:
  - 用户账号已存在
test_data:
  username: alice
  password: "${env:TEST_PASSWORD}"   # 机密必须用引用

steps:
  - 打开登录页
  - 输入账号密码
  - 点击登录
expected:
  - 跳转首页
  - 显示用户昵称

assertions:
  - selector: "[data-testid=username-display]"
    equals: "alice"

automation:
  status: implemented    # implemented | scaffolded | manual | not_applicable
  framework: playwright
  file: tests/system/login.spec.ts
  test_id: login_with_valid_credentials

targets:                 # 由 Adapter/Indexer 自动维护
  files: [src/pages/login.tsx, src/api/auth.ts]
  symbols: [LoginPage, authenticate]

regression_tags: [auth, smoke]
notes: ""
```

#### `qa/bugs/<id>.yml` —— 缺陷记录

```yaml
id: BUG-001
title: 登录后昵称未渲染
state: open                # open | fixed | verified | wont_fix
severity: high             # blocker | high | medium | low
priority: P1
related_cases: [TC-LOGIN-003]
related_requirements: [REQ-101]
repro_steps:
  - 用户登录后
  - 观察首页右上角
expected: 显示用户昵称
actual: 显示 undefined
suspected_cause: |
  authenticate() 返回值缺少 nickname 字段
needs_regression: true
created_at: 2026-06-17T10:00:00+08:00
created_by: designer_runner
```

#### `qa/run/last.json` —— 最新运行状态

包含：模式、选中用例、执行结果、checkpoint（L3 恢复用）、Gatekeeper 判定结果。

#### `qa/final_test_report.md` —— 测试报告

```markdown
# 测试报告

运行模式: L1
运行 ID: run_20260617_103000
开始时间: ...
结束时间: ...

## 执行统计
总数: 10 / 通过: 8 / 失败: 2 / 跳过: 0 / Flaky: 0

按层级:
- 单元测试: 4/4
- 集成测试: 2/2
- 系统测试: 2/4
- 验收测试: 0/0

## 失败用例
- BUG-001: 登录后昵称未渲染 (TC-LOGIN-003, severity=high)

## 未覆盖需求
- REQ-105: 记住密码功能

## 未能验证的事项
- 性能测试：未在 L1 模式下执行

## 判定结论
结论: FAIL
理由: 存在 1 个 P1 用例失败
```

#### `qa/release_gate_report.md` —— L3 发版门报告（仅 L3 生成）

含 8 phase 检查点完成情况、维度覆盖、未覆盖维度、自检清单 8 项、最终结论。

## 4. 日常使用流程

### 4.1 标准开发流程

```text
1. 开发功能
   ↓
2. /qa feature <功能名>     # L1 验证
   ↓
3. 如有失败 → 修代码 → /qa retry
   ↓
4. 模块完成 → /qa module <模块名>     # L2 验证
   ↓
5. 发版前 → /qa release     # L3 完整质量门
   ↓
6. PASS → 发版
```

### 4.2 修 Bug 流程

```text
1. 发现 Bug：
   - Agent 自动登记 → qa/bugs/BUG-XXX.yml
   - 或用户手动登记
   ↓
2. 修代码
   ↓
3. /qa bugfix BUG-XXX     # L4 验证
   ↓
4. PASS → bug 标记 verified
   FAIL → 回到步骤 2（最多 5 轮）
```

### 4.3 支持的命令引用形式

```bash
/qa bugfix BUG-008                          # Bug ID（最常用）
/qa bugfix TC-LOGIN-003                     # 用例 ID（反查关联 bug）
/qa bugfix #123                             # Issue 编号
/qa bugfix 登录后昵称                         # 关键词模糊匹配
/qa bugfix "用户登录后首页没显示昵称"           # 自然语言（自动创建 bug 记录）
```

## 5. 需求文档配置

### 5.1 自动发现（零配置）

`qa init` 时自动扫描以下路径（按优先级）：

| 框架/约定 | 路径 |
|---|---|
| 通用 docs | `docs/requirements.md`, `docs/PRD.md`, `docs/design.md` |
| **ai-docs 工业级 AI 工作流** | **`ai-docs/prd/*.md`**, **`ai-docs/architecture/*.md`**, **`ai-docs/apis/*.md`** |
| **ai-docs 通用** | `ai-docs/*.md`（根目录 md 文件） |
| BMAD | `.bmad/output/*.md` |
| spec-kit | `specs/*/spec.md`, `specs/*/acceptance.feature` |
| BDD | `features/*.feature` |
| 项目根 | `REQUIREMENTS.md`, `PRD.md`, `SPEC.md` |

**汇总文件优先**：
- `*-all.md`（如 `prd-all.md`, `api-all.md`）
- `*-overview.md`（如 `architecture-overview.md`）
- 含 "总"/"全量"/"汇总"/"概览" 的中文名

### 5.2 动态指定路径（命令时）

⭐ **典型场景**：版本切换、临时使用其他目录

#### 方式 1：自然语言（在 Claude Code 中）

```
/qa feature 短信绑定 需求文档在 doc/v2026-06-17-当前版本文档/
/qa feature 登录 文档在 D:\AndroidProject\ClawBoxClient\ai-docs\prd\
/qa module 订单 doc-path=ai-docs/v3.0.0
```

Subagent 解析后自动调用：
```bash
python -m qa_agent.cli.main prepare --mode L1 --scope 短信绑定 \
  --docs-path "doc/v2026-06-17-当前版本文档/"
```

#### 方式 2：命令行直接指定

```bash
qa feature 短信绑定 --docs-path doc/v2026-06-17-当前版本文档/

# 多个目录
qa feature 支付 \
  --docs-path doc/v2026-06-17/需求/ \
  --docs-path doc/v2026-06-17/设计/
```

### 5.3 文档自动分类

Subagent 扫描指定目录后，按以下规则分类：

#### 子目录名优先（强信号）
| 子目录 | 分类 |
|---|---|
| `prd/`, `requirements/`, `需求/`, `产品需求/` | 需求 |
| `design/`, `architecture/`, `arch/`, `设计/`, `架构/` | 设计 |
| `api/`, `apis/`, `contracts/`, `接口/` | API |
| `acceptance/`, `testing/`, `验收/`, `测试/` | 验收 |

#### 文件名关键词（中弱信号）
| 类别 | 英文关键词 | 中文关键词 |
|---|---|---|
| **需求** | requirement, req, prd, spec, user-story, story, feature, epic, backlog | 需求, 规格, 故事, 产品需求, 功能 |
| **设计** | design, architecture, arch, tech, technical, data-model, sequence | 设计, 架构, 技术方案, 数据模型, 流程, 领域 |
| **API** | api, endpoint, rest, graphql, rpc, contract, openapi, swagger | 接口, 协议, 契约 |
| **验收** | acceptance, criteria, gherkin | 验收 |

#### 排除关键词（不分类）
README, CHANGELOG, LICENSE, TODO, history, meeting, minutes, log, note, draft, 会议, 记录, 草稿, 历史

## 6. 运行模式详解

### 6.1 L0 Spot — 最快验证

**触发场景**：
- 改了一行代码想看看是否搞坏了
- 调试时验证某个修改

**执行内容**：
- ⏭️ 跳过设计阶段
- ▶️ 只跑：受影响的单元测试 + 关联冒烟测试
- ⏭️ 不跑：集成、系统、E2E
- ⚡ 算法判定（不调 LLM）

**典型耗时**：10-30 秒

**适合**：改个变量名、调一个内部函数、修笔误
**不适合**：修业务 bug、发版前

### 6.2 L1 Feature — 一个功能开发完

**触发场景**：刚做完一个新功能（如"用户登录"）

**执行内容**：
- 📝 Designer 增量补该功能用例（如有新需求）
- 🔍 影响面分析
- ▶️ 跑：该功能全部分层用例（unit + integration + system + acceptance）
- ▶️ 跑：邻接回归
- 🎯 Gatekeeper 判定

**典型耗时**：1-5 分钟

### 6.3 L2 Module — 模块完成

**触发场景**：一个模块或一次迭代完成

**执行内容**：
- 📝 Designer 复核该模块所有用例完整性
- 🔍 影响面分析（深度更广）
- ▶️ 跑：该模块全部用例 + 跨模块集成
- 🧬 抽样 mutation testing
- 🛡️ 对抗式 review（构造"实现错但用例 PASS"的反例）
- 🎯 Gatekeeper 判定

**典型耗时**：10-30 分钟

### 6.4 L3 Release — 发版门 ⭐

**触发场景**：准备发版 / 交付验收

**执行内容（最完整）**：
- 📝 Designer 校验需求追踪矩阵 100% 覆盖
- 🔍 影响面分析（不限深度）
- ▶️ 跑：全部分层用例
- ⚡ 跑：依赖审计（npm audit / pip-audit）
- 🔒 跑：静态安全扫描（bandit / semgrep）
- 🧬 Mutation testing（仅 diff 涉及代码）
- 🔄 Flaky 检测（失败用例隔离重跑）
- 🛡️ 对抗式 review
- 🎯 Gatekeeper 完整质量门判定

**典型耗时**：30 分钟 - 2 小时

**唯一可作发版凭据的模式** ⭐

#### L3 命令行扩展参数

```bash
# 默认 L3（依赖审计 + 静态安全）
/qa release

# 加入动态安全扫描（ZAP）
qa release --with-dynamic-security

# 加入性能压测
qa release --with-performance

# 加入兼容性矩阵
qa release --with-compatibility

# 全开（1-2 小时）
qa release --with-all-nonfunctional

# 跳过某些维度（必须在 release_gate_report 登记）
qa release --skip compatibility --skip performance
```

#### L3 检查点恢复

L3 长时间运行支持中断恢复：

```bash
# 跑 L3
/qa release

# Ctrl+C 中断（或电脑休眠）
^C
[Agent] 中断信号收到，已保存检查点
[Agent] 下次运行 /qa resume 可从此处继续

# 第二天恢复
/qa resume
[Agent] 检测到未完成的 L3 运行
[Agent] 已完成：Phase 1-3
[Agent] 待执行：Phase 4-8
是否继续？(yes/重新开始/取消)：
```

### 6.5 L4 Bugfix — 修 Bug 验证

**触发场景**：修复了一个 bug，想验证修好了 + 没破坏其他东西

**执行内容**：
- ⏭️ 不做设计
- 📍 定位失败用例（Bug 复现用例）
- 🔍 影响面分析：基于这次 fix 的代码变更
- ▶️ 跑：bug 复现用例（确认 fix 有效）
- ▶️ 跑：受影响的全部分层用例（unit/integration/**system**/acceptance）
- 🎯 Gatekeeper 判定 bug 是否 verified

**典型耗时**：3-15 分钟

**会跑真实 E2E 测试** ✅

#### 修 Bug 流程示例

```text
场景：修复 BUG-008（登录后昵称未渲染）
修改文件：src/api/auth.ts

跑 /qa bugfix BUG-008 后：

[Agent] 解析 bug 引用 → BUG-008
[Agent] 加载 bug 详情：登录后昵称未渲染（TC-LOGIN-003 暴露）
[Agent] 影响面分析（CodeGraph）：
  变更符号：authenticate, validateCredentials
  反查命中：
    - TC-LOGIN-001 (system, P0) ← 真实 Playwright E2E
    - TC-LOGIN-003 (system, P1) ← bug 复现用例
    - TC-LOGIN-005 (integration, P1) ← API 集成测试
    - TC-AUTH-002 (unit, P0)
    - TC-AUTH-004 (unit, P1)
  
[Adapter] 启动 Playwright 真实浏览器
[Adapter] 启动后端服务...
[Adapter] 执行 5 条用例...
  ✓ TC-LOGIN-001 PASS (2.3s)
  ✓ TC-LOGIN-003 PASS (1.8s) ← bug fix 验证
```

## 8. 故障排查

### 8.1 CodeGraph 不可用

**症状**：
```
RuntimeError: CodeGraph 不可用
配置的 MCP 工具前缀（按优先级）: mcp__codegraph
```

**解决**：

1. **未安装/未索引**：
   ```bash
   npm i -g @colbymchenry/codegraph   # 安装 CLI
   codegraph install                  # 连接 agent
   codegraph init                     # 在项目建索引（之后自动同步）
   ```

2. **本机 MCP 服务名不同**：
   ```yaml
   codegraph:
     mcp_tool_prefixes: ['mcp__your_service_name']
   ```

3. **MCP 服务未启动**：检查 Claude Code 的 MCP 配置

4. **临时切到 local 模式**：
   ```bash
   /qa feature 登录 --impact=local
   # 或在 .qa-agent.yml 设置 impact_analysis: local
   ```

### 8.2 需求文档未识别

**症状**：
```
[需求发现] 未找到需求文档
[L3] BLOCKED: 需求文档不存在
```

**解决**：

1. **检查文档位置**：
   ```bash
   qa discover-docs --path your-doc-dir/
   # 输出分类结果
   ```

2. **临时指定路径**：
   ```
   /qa feature 登录 需求文档在 你的文档路径/
   ```

3. **显式配置**：
   ```yaml
   requirements:
     primary: your-doc/req.md
   ```

### 8.3 测试执行失败但不是代码问题

**症状**：`failure_kind: env`（环境问题），如：
- "No devices found"（Android 模拟器未启动）
- "Connection refused"（数据库未启动）

**Agent 行为**：自动标 `BLOCKED` 而不是 `FAIL`，不阻断下层执行

**解决**：
- 启动依赖：`adb start-server`（Android）/ `docker-compose up`（DB）
- 然后：`/qa retry`

### 8.4 Adapter 检测失败

**症状**：
```
[Adapter] 无法识别项目类型，使用 Generic Adapter
```

**解决**：

1. **手动指定**：
   ```yaml
   project_type: mobile             # 或 web/backend/generic
   ```

2. **Generic 兜底**：
   ```yaml
   project_type: generic
   commands:
     unit: ./run-tests.sh
     integration: make test
   ```

### 8.5 Windows 编码问题

**症状**：`UnicodeEncodeError: 'gbk' codec`

**解决**：CLI 已自动设置 UTF-8，如仍报错：
```powershell
[System.Console]::OutputEncoding = [System.Text.Encoding]::UTF8
$env:PYTHONIOENCODING = "utf-8"
```

## 9. 进阶用法

### 9.1 用户扩充执行集

Agent 不允许缩减用户选择，但用户可扩充：

```bash
qa feature 登录 --cases TC-LOGIN-001,TC-LOGIN-002
# 在自动选择的基础上额外加入
```

### 9.2 Waiver（风险接受）

```yaml
# qa/waivers.yml
- case_id: TC-LOGIN-099
  reason: 该测试在 CI 环境不稳定，已在本地手动验证
  waived_until: 2026-07-15
  severity: low
```

⚠️ **限制**：
- 安全用例 critical/high **禁止 waiver**
- low/medium 安全 waiver 必须附 `evidence` 文件证明不可达
- 过期自动失效

### 9.3 修复轮触发模式

```yaml
repair_loop:
  mode: manual                            # 默认（个人项目推荐）
  # mode: auto-dev                        # 自动调用 Dev Agent 修
  # mode: auto-fixer                      # QA 自修（不推荐，自审风险）
```

**manual 流程**：
1. Runner 失败 → 报告 + 退出
2. 你修代码
3. `/qa retry`
4. 重跑相同 selection

### 9.4 调用 Subagent 工具命令

```bash
# 仅准备影响面分析，不执行
qa prepare --mode L1 --scope 登录

# 仅扫描某目录的文档分类
qa discover-docs --path doc/v2026-06-17/

# 解析 bug 引用
qa resolve-bugfix --ref "登录后昵称没显示"

# 算法判定（L0/L4 用）
qa judge --mode L0

# 生成测试脚本骨架
qa scaffold --case TC-LOGIN-001
```
